## Fuzzer와 Fuzzing
---

Fuzzing은 프로그램에 비정상적이거나 예상하지 못한 입력을 반복해서 넣어보면서 크래시, 멈춤, 메모리 오류 같은 문제를 찾는 소프트웨어 테스트 기법이다. 이때 입력을 만들어 프로그램에 넣어주는 도구를 Fuzzer(퍼저)라고 한다.

일반적인 테스트는 개발자가 예상한 정상 입력과 몇 가지 경계값을 중심으로 검사한다. 하지만 실제 사용자가 보내는 입력은 형식이 깨져 있거나 크기가 지나치게 크거나, 필드 조합이 이상할 수 있다. 이런 입력을 사람이 모두 직접 만들기 어렵기 때문에 퍼저가 자동으로 많은 입력을 생성하고 실행해 본다.

여기서 중요한 점은 퍼징이 단순히 랜덤 데이터를 계속 넣는 것만을 뜻하지 않는다는 것이다. 대상 프로그램이 어떤 입력을 받는지, 실행 중 어떤 코드 경로를 밟았는지, 어떤 오류를 감지할지에 따라 퍼징 방법과 효율이 달라진다.

### Fuzzing의 기본 동작
---

퍼징은 보통 다음과 같은 흐름으로 진행된다.

1. 대상 프로그램과 입력 형식을 정한다.
2. 시작 입력(seed corpus)을 준비한다.
3. 퍼저가 입력을 변형하거나 새 입력을 생성한다.
4. 대상 프로그램에 입력을 전달하고 실행 결과를 관찰한다.
5. 새로운 코드 경로를 실행했거나 오류가 발생한 입력을 저장한다.
6. 저장된 입력을 다시 변형하면서 더 많은 경로를 탐색한다.

예를 들어 이미지 파서를 퍼징한다고 하자. 처음부터 임의의 바이트만 넣으면 대부분의 입력이 파일 헤더 검사에서 거부되어 실제 이미지 디코딩 코드까지 도달하지 못할 수 있다. 유효한 PNG 파일 몇 개를 시작 입력으로 주면 퍼저가 해당 파일의 청크 길이, 색상 형식, 압축 데이터 등을 조금씩 바꾸면서 더 깊은 코드까지 도달할 가능성이 높아진다.

이처럼 시작 입력의 모음을 corpus 또는 seed corpus라고 한다. 시작 입력이 다양하고 유효한 구조를 잘 포함할수록 퍼저가 깊은 코드 경로를 탐색하는 데 도움이 된다.

### Fuzzer가 찾는 오류
---

퍼저가 오류를 발견했다고 판단하는 기준은 도구와 설정에 따라 다르다. 흔히 다음과 같은 결과를 확인한다.

- **Crash**: 프로그램이 비정상 종료되는 경우
- **Timeout / Hang**: 입력 처리에 지나치게 오래 걸리거나 멈춘 것처럼 보이는 경우
- **메모리 오류**: out-of-bounds access, use-after-free, double-free 등
- **정의되지 않은 동작**: 정수 오버플로, 잘못된 포인터 사용 등
- **예상하지 못한 동작**: 잘못된 결과, assertion 실패, 상태 불일치 등

단순히 프로그램이 죽었다는 사실만으로 보안 취약점이라고 확정할 수는 없다. 재현이 되는지 확인하고, 오류가 발생한 위치와 영향 범위를 분석해야 한다. 반대로 프로그램이 크래시하지 않아도 메모리 손상이나 잘못된 상태 처리가 발생할 수 있기 때문에 Sanitizer 같은 런타임 검사를 함께 사용하는 것이 중요하다.

AddressSanitizer(ASan)는 버퍼 오버플로와 use-after-free 같은 메모리 오류를 찾는 데 도움을 주고, UndefinedBehaviorSanitizer(UBSan)는 signed integer overflow 등 C/C++의 정의되지 않은 동작을 감지하는 데 사용된다. Google의 fuzzing 문서에서도 퍼징 타겟을 Sanitizer와 함께 빌드하는 것을 권장한다.

### Fuzzing의 분류
---

퍼징은 한 가지 기준만으로 나뉘지 않는다. 입력을 어떻게 만드는지, 프로그램에 대한 정보를 얼마나 활용하는지, 실행 방식을 어떻게 구성하는지에 따라 여러 분류가 있다. 그래서 아래 분류들은 서로 배타적인 종류라기보다 조합 가능한 특성이라고 보면 된다.

#### 입력 생성 방식에 따른 분류

##### Mutation-based Fuzzing

기존에 준비한 입력을 조금씩 변형해 새로운 입력을 만드는 방식이다. 바이트를 뒤집거나, 값을 덧붙이거나, 잘라내거나, 작은 정수 값을 바꾸는 방법 등이 있다.

장점은 실제 포맷의 유효한 입력을 시작점으로 사용할 수 있다는 것이다. 반면 입력 구조가 복잡하면 작은 변형만으로는 파서의 깊은 부분까지 도달하지 못할 수 있다. 예를 들어 파일 길이 필드와 실제 데이터 길이가 맞지 않으면 파서가 본문을 읽기 전에 입력을 거부할 수 있다.

##### Generation-based Fuzzing

입력 형식의 문법(schema, grammar)이나 프로토콜 규칙을 정의한 뒤, 그 규칙에 맞는 입력을 새로 생성하는 방식이다. JSON, XML, SQL, 네트워크 프로토콜처럼 구조가 명확한 입력을 만들 때 유용하다.

형식에 맞는 입력을 많이 만들 수 있어 파서의 깊은 로직까지 진입하기 쉽다. 하지만 문법이나 제약 조건을 사람이 작성해야 하므로 준비 비용이 들고, 문법이 실제 구현과 다르면 유효하지 않은 입력만 계속 만들어질 수 있다.

##### Grammar-aware / Structure-aware Fuzzing

Mutation 기반 퍼징과 generation 기반 퍼징 사이의 접근이다. 입력의 문법이나 구조 정보를 이용해 기존 입력을 변형하거나 유효한 새 입력을 생성한다. 단순 바이트 변형으로는 도달하기 어려운 복잡한 포맷에 유용하다.

Google의 fuzzing 문서에서도 일부 입력 형식은 일반 퍼저가 효율적으로 변형하기 어려워, 구조를 알려주거나 사용자 정의 mutator를 만드는 것이 도움이 될 수 있다고 설명한다.

#### 프로그램 피드백 활용 여부에 따른 분류

##### Black-box Fuzzing

대상 프로그램 내부 구조나 코드 커버리지 정보를 거의 사용하지 않고 입력과 외부 결과만으로 테스트한다. 소스 코드가 없어도 적용할 수 있고 설정이 비교적 간단하다. 대신 입력이 실제로 새로운 코드 경로에 도달했는지 알기 어려워 탐색 효율이 낮을 수 있다.

##### Coverage-guided Fuzzing

입력 실행 중 어떤 코드 경로(coverage)가 실행됐는지 확인하고, 새로운 경로나 상태를 발견한 입력을 corpus에 추가해 다음 변형에 활용한다. 퍼저가 단순히 무작위 입력을 생성하는 것이 아니라, 실행 결과를 피드백으로 받아 탐색을 이어가는 방식이다.

AFL++의 기본 접근을 단순화하면 다음과 같다.

1. corpus에서 입력 하나를 선택한다.
2. 입력을 줄여도 동일한 동작을 보이는지 확인하고 불필요한 부분을 줄인다.
3. 여러 변형 기법으로 새로운 입력을 만든다.
4. 실행 결과에서 새로운 coverage가 관찰되면 해당 입력을 corpus에 추가한다.
5. 저장된 입력을 다시 선택해 이 과정을 반복한다.

이 방식은 instrumentation이 필요할 수 있다. 소스 코드가 있으면 컴파일 과정에서 계측 코드를 넣을 수 있고, 바이너리만 있으면 에뮬레이션이나 동적 바이너리 계측을 이용하는 도구를 사용할 수 있다.

##### Sanitizer-guided Fuzzing

Coverage 피드백뿐 아니라 Sanitizer가 잡아내는 메모리·정의되지 않은 동작 오류를 함께 활용하는 방식이다. Coverage-guided fuzzing과 결합해서 사용하는 경우가 많으며, 퍼저 자체가 버그를 만들기보다 런타임 검사기가 오류 조건을 감지하고 퍼저가 이를 재현하는 입력을 찾도록 돕는다.

#### 실행 방식에 따른 분류

##### In-process Fuzzing

대상 함수를 한 프로세스 안에서 반복 호출하면서 많은 입력을 처리하는 방식이다. 프로세스를 매번 새로 실행하는 비용을 줄일 수 있어 빠르다. 대신 각 입력 처리 후 프로그램 상태가 초기화되어야 하고, 한 입력에서 발생한 상태 오염이 다음 입력에 영향을 주지 않도록 fuzz target을 잘 작성해야 한다.

libFuzzer는 대표적인 in-process, coverage-guided, evolutionary fuzzing engine이다. 테스트할 라이브러리와 함께 링크되고, 정해진 진입점 함수에 입력 바이트를 전달한다. 각 입력은 프로세스 내부에서 반복 처리되므로 대상 함수는 비정상 입력을 받아도 프로세스를 종료하지 않아야 하고, 가능한 한 빠르고 결정적으로 동작해야 한다.

##### Process-per-testcase Fuzzing

각 입력마다 새 프로세스를 실행하는 방식이다. 테스트 간 상태가 분리되어 안정적으로 동작하고 기존 명령행 프로그램을 대상으로 구성하기 쉽다. 대신 프로세스 생성·종료 비용이 반복되어 in-process 방식보다 느려질 수 있다.

AFL 계열 도구는 forkserver 등으로 프로세스 시작 비용을 줄이는 기법을 사용한다. AFL++는 소스 계측뿐 아니라 QEMU, FRIDA 등 여러 모드로 바이너리를 테스트할 수 있다.

##### Persistent Mode

한 프로세스를 유지하면서 대상 함수나 처리 루프를 여러 번 실행하는 최적화 방식이다. 매 입력마다 새 프로세스를 띄우는 비용을 줄여 실행 속도를 높일 수 있다. 하지만 입력마다 상태를 깨끗하게 초기화하지 못하면 이전 테스트의 상태가 다음 입력에 영향을 주는 문제가 생긴다. 속도가 빨라지는 대신 안정성 검증이 더 중요하다.

### 대표적인 Fuzzer 비교
---

#### AFL++

AFL++는 AFL 계열의 오픈소스 퍼징 프레임워크다. 소스 코드가 있는 경우 LLVM 기반 instrumentation 등을 사용할 수 있고, 바이너리만 있는 경우 QEMU, FRIDA 같은 모드를 활용할 수도 있다. coverage 기반 corpus 관리, 여러 mutation 전략, persistent mode, CmpLog 등 여러 기능을 제공한다.

장점은 적용 가능한 모드와 설정이 다양하고, 문서와 사용 사례가 많다는 점이다. 소스 코드가 없어도 일부 환경에서 바이너리를 퍼징할 수 있다. 반면 가장 효율적인 설정을 고르려면 타겟 구조와 빌드 환경을 이해해야 하며, 초기 입력 corpus와 harness 품질에 따라 결과가 크게 달라진다.

공식 문서의 기본 흐름은 타겟 계측, 시작 corpus 준비, 입력 변형과 coverage 확인 순서다. seed corpus가 중요하며, 중복 경로를 만드는 입력을 줄이고 필요하면 corpus를 최소화하는 작업도 한다.

#### libFuzzer

libFuzzer는 LLVM의 in-process coverage-guided 퍼징 엔진이다. 테스트 대상 라이브러리와 연결해 `LLVMFuzzerTestOneInput` 같은 진입점에 입력을 전달한다. 라이브러리 API 단위로 빠르게 반복 테스트하고 싶을 때 적합하다.

간단한 fuzz target의 형태는 다음과 같다.

```cpp
#include <cstddef>
#include <cstdint>

extern "C" int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    // 테스트할 API에 임의의 입력을 전달한다.
    // 예: ParseImage(data, size);
    return 0;
}
```

중요한 점은 target 함수가 빈 입력, 잘못된 형식, 큰 입력을 받아도 안전하게 처리해야 한다는 것이다. `exit()`을 호출하거나 비결정적으로 동작하면 퍼징 효율이 떨어질 수 있다. libFuzzer는 ASan/UBSan 같은 Sanitizer와 함께 사용하기 쉽다는 장점이 있다. 반면 in-process 형태에 맞게 테스트 함수를 작성해야 하므로 기존 CLI 프로그램을 그대로 테스트하기 어려울 수 있다.

LLVM 문서 기준으로 libFuzzer의 원 저자들은 새로운 기능 개발을 Centipede로 옮겼고, libFuzzer는 중요한 버그 수정 중심으로 유지되고 있다. 따라서 신규 프로젝트라면 LLVM 문서에서 현재 지원 상태와 대안을 함께 확인하는 것이 좋다.

#### Jackalope

Jackalope는 Google Project Zero에서 공개한 커스터마이즈 가능한 coverage-guided binary fuzzer다. 소스 코드가 없어도 Windows, macOS, Linux, Android의 바이너리를 대상으로 할 수 있고, 기본적으로 TinyInst 기반 계측과 파일 또는 shared memory 입력 전달을 제공한다.

특히 기존의 일반 퍼저를 적용하기 어려운 바이너리 타겟에서 instrumentation, mutator, 입력 전달 방식을 사용자 목적에 맞게 조정할 수 있다는 점이 특징이다. 단일 머신의 여러 스레드뿐 아니라 서버-워커 구조로 여러 머신에 퍼징 작업을 분산할 수도 있다.

다만 바이너리 퍼징은 타겟 함수, 모듈, 입력 전달 방식 등을 직접 파악해야 하는 경우가 많아 설정 난이도가 낮다고만 보기는 어렵다. 소스 코드 기반 퍼징과 달리 계측 범위를 어떻게 잡는지도 중요하다.

#### Honggfuzz

Honggfuzz는 여러 입력 전달 방식과 커스터마이징을 제공하는 퍼저다. Google의 fuzzing 문서는 libFuzzer처럼 단순한 라이브러리 단위의 target 작성 방식이 맞지 않거나, 입력을 명령행·stdin·네트워크 서버 등으로 전달해야 하는 복잡한 프로젝트에서 Honggfuzz를 고려할 수 있다고 소개한다.

#### OSS-Fuzz

OSS-Fuzz는 특정 퍼징 엔진 하나의 이름이라기보다, 오픈소스 프로젝트의 퍼징을 지속적으로 실행하고 결과를 관리하는 서비스/인프라에 가깝다. libFuzzer, AFL++, Honggfuzz, Centipede 등 엔진과 Sanitizer를 조합해 프로젝트를 지속적으로 테스트한다.

즉 AFL++나 libFuzzer가 입력을 생성하고 탐색하는 엔진이라면, OSS-Fuzz는 여러 프로젝트를 대상으로 빌드·실행·크래시 보고·회귀 테스트를 운영하는 플랫폼으로 볼 수 있다.

### 도구별 비교 요약
---

| 구분 | AFL++ | libFuzzer | Jackalope | Honggfuzz |
| --- | --- | --- | --- | --- |
| 주된 형태 | coverage-guided, 여러 실행 모드 | in-process, coverage-guided | 바이너리 coverage-guided | 다양한 입력 전달·커스터마이징 |
| 소스 코드 | 있으면 효율적인 계측 가능, 바이너리 모드도 지원 | 보통 소스와 Clang 빌드가 필요 | 바이너리 타겟 중심, Linux SanitizerCoverage 모드도 있음 | 구성에 따라 다름 |
| 입력 대상 | 파일/표준 입력 등 | fuzz target 함수 | 파일/shared memory 등 | 파일, stdin, 네트워크 등 구성 가능 |
| 장점 | 모드와 기능이 다양하고 자료가 많음 | 라이브러리 API 테스트가 간단하고 빠름 | 블랙박스 바이너리 타겟에 유연함 | 복잡한 입력 전달과 사용자 정의에 유리 |
| 고려할 점 | 빌드·계측·corpus 설정이 필요 | in-process target을 작성해야 함 | 바이너리 계측과 harness 설정이 필요 | 프로젝트에 맞춘 설정·통합이 필요 |

도구가 많다고 해서 하나의 도구가 항상 가장 좋은 것은 아니다. 소스 코드가 있는 라이브러리 API라면 libFuzzer가 간단할 수 있고, 프로그램 전체나 바이너리만 있는 대상을 다루면 AFL++ 또는 Jackalope가 더 적합할 수 있다. 네트워크 입력이나 특수한 전달 방식이 필요하면 Honggfuzz처럼 유연한 구성이 가능한 도구도 후보가 된다.

### Fuzzing에서 중요한 요소
---

#### 좋은 Fuzz Target

퍼저가 입력을 전달할 수 있는 함수나 실행 단위를 fuzz target이라고 한다. target은 가능한 한 한 가지 기능을 집중적으로 테스트하고, 입력 하나를 빠르게 처리하며, 잘못된 입력을 받아도 프로세스를 정상적으로 이어가야 한다.

타겟이 너무 넓으면 시작 단계에서 복잡한 초기화만 반복하거나 입력이 실제 처리 코드에 도달하지 못할 수 있다. 반대로 너무 좁으면 실제 사용 경로에서 발생하는 상호작용을 놓칠 수 있다. 그래서 어떤 함수와 입력 경계를 테스트할지 정하는 것이 중요하다.

#### Seed Corpus와 Dictionary

시작 corpus는 퍼저가 변형을 시작할 입력 모음이다. 유효한 파일, 테스트 케이스, 과거에 발견한 흥미로운 입력 등을 넣을 수 있다. 많은 파일을 무작정 넣는 것보다 서로 다른 코드 경로를 여는 작고 다양한 입력이 유용하다.

Dictionary는 입력 형식에서 의미가 있는 토큰을 퍼저에게 알려주는 목록이다. 예를 들어 프로토콜의 명령어, 파일 포맷의 chunk 이름, JSON 키 등이 해당된다. 무작위 바이트만으로 특정 문자열 비교를 통과하기 어려운 경우 도움이 된다.

#### Coverage와 Crash Triage

Coverage는 퍼저가 어떤 코드 경로나 분기까지 도달했는지 보는 지표다. 높은 coverage가 곧 취약점 발견을 의미하지는 않지만, 입력이 실제로 대상 기능을 탐색하고 있는지 판단하는 데 도움이 된다.

크래시가 발견되면 입력을 최소화하고 재현 여부를 확인한다. 여러 입력이 동일한 원인으로 발생한 크래시인지 분류하고, Sanitizer 로그와 디버거를 통해 실제 오류 지점을 분석한다. 동일한 원인의 크래시를 하나로 묶는 작업을 deduplication이라고 부른다.

### 장점과 한계
---

Fuzzing의 장점은 사람이 미리 생각하지 못한 입력 조합을 대량으로 자동 테스트할 수 있다는 점이다. 반복 실행이 가능하고, 발견한 입력을 저장해 회귀 테스트로 사용할 수 있다. Sanitizer와 함께 사용하면 정상 입력 테스트만으로 찾기 어려운 메모리 오류를 발견하는 데 도움이 된다.

반면 퍼징이 모든 버그를 찾아주는 것은 아니다. 입력이 깊은 로직에 도달하지 못하면 해당 영역은 테스트되지 않는다. 암호화, 체크섬, 압축 등으로 입력이 감싸져 있으면 단순 변형만으로 유효한 내부 데이터에 도달하기 어렵다. 또한 환경 설정, harness, corpus, 실행 시간에 따라 결과가 크게 달라진다.

따라서 “몇 시간 퍼징했는데 크래시가 없었다”가 “취약점이 없다”는 뜻은 아니다. 선택한 입력 경로와 코드 coverage, 오류 탐지 설정 범위 안에서 재현 가능한 버그가 발견되지 않았다는 의미로 해석해야 한다.

### Bug Bounty에서의 활용
---

Bug Bounty에서 퍼징은 공개된 프로그램에 무작정 트래픽을 보내는 도구가 아니다. 먼저 프로그램 범위와 테스트 허용 정책을 확인하고, 허가된 로컬 바이너리·라이브러리·테스트 환경 또는 명시적으로 허용된 타겟에서 사용해야 한다.

소스 코드가 있는 오픈소스 구성요소라면 parser나 파일 처리 라이브러리에 fuzz target을 만들고, 발견한 크래시를 재현한 뒤 보안 영향이 있는지 분석할 수 있다. 바이너리만 제공되는 경우에는 Jackalope나 AFL++의 바이너리 모드 같은 선택지가 있지만, 대상의 입력 경로와 계측 방식을 파악해야 한다.

발견 결과를 보고할 때는 최소 재현 입력, 실행 환경, 재현 절차, Sanitizer 또는 디버거 로그, 영향을 받는 버전 등을 함께 정리한다. 단순한 crash가 원격 공격으로 이어지는지, 권한이나 데이터에 어떤 영향이 있는지는 별도로 검증해야 한다.

### 정리
---

Fuzzing은 자동으로 다양한 입력을 만들고 프로그램에 반복 전달하여 오류를 찾는 테스트 기법이다. Mutation/generation, black-box/coverage-guided, in-process/process-per-testcase 등 여러 분류가 있으며 실제 도구는 이 특징들을 조합해서 제공한다.

AFL++는 다양한 계측 및 실행 모드를 제공하고, libFuzzer는 라이브러리 API를 in-process로 테스트하기 편하며, Jackalope는 소스 코드가 없는 바이너리 타겟을 커스터마이즈해서 퍼징하는 데 초점을 둔다. OSS-Fuzz는 여러 엔진을 프로젝트에 지속적으로 적용하는 플랫폼이다.

결국 퍼저 선택만큼 중요한 것은 적절한 fuzz target, 좋은 seed corpus, Sanitizer 설정, 그리고 발견한 크래시를 재현하고 원인을 분석하는 과정이다.
